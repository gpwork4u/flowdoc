# 設計規則

這些規則來自實際做過的幾份文件與使用者的修正意見。renderer 盡量把它們變成預設行為，verify 把能機械檢查的變成檢查項；其餘靠撰寫 `.flow` 的人遵守。

## 結構

1. **依使用者行為分段，一段一張圖。** 不同行為（上架、發佈變更、下架、backfill、後續查詢）不要擠在同一張圖上靠點亮區分。
2. **圖上只畫這一段用到的元件。** 沒用到的 service 不顯示；狀態卡也只列這一段用得到的。
3. **每段 2–8 步。** 少於 2 步就併到別段；多於 10 步讀者會失去位置感，拆段。
4. **一整頁只有一個 ★。** 分歧點是真正的設計決定，其他步驟都是它的連帶結果。
5. 情境分頁（PART 1…N）與步驟點（1…N）都要能直接點擊跳轉；靜止時停在第 1 段第 1 步，不能是空白狀態。

## 顏色（三個語意，不要再多）

| 顏色 | 只用在 |
|---|---|
| 主色 signal（青） | 這一步正在發生：點亮的框、連線、亮起的卡 |
| 第二色 clay（褐） | 刻意不走、已刪除或失效：ghost、`!gone`、old chip |
| 橘色 chg | 要新增或修改的地方：`changed` 實線框，不隨播放變暗 |

橘框以外的地方一律不用橘色；ghost 是虛線、changed 是實線，兩者不能長得像。

## 文字

1. **readout 說「為什麼」，不說「做什麼」。** 圖已經說了做什麼；說明要講這一步為什麼在這裡、換個順序會壞在哪、失敗會怎樣。
2. **不要過多文字敘述。** 使用者明確要求過：動畫為主，說明精簡。desc 建議 ≤ 120 字。
3. **標籤不能被框擋住。** 標籤畫在所有元件之上，加一圈底色描邊；仍要避開框（renderer 自動放置，verify 檢查）。
4. 標籤用白話，不用「×2」這類需要解釋的符號；同一件事做兩次就寫清楚是哪兩件。
5. 示意資料要標明「示意」，不可冒充真實數據。有真實數據（實測的大小、時間、id 前綴）就優先用真實的。示意的 id 用 `alias` 宣告，驗收腳本才知道要換成真實資料。
6. **狀態卡只放狀態，說明用 note。** 卡片內容會變成驗收腳本的斷言；比較、判斷、「不變」這類給讀者看的字用 `note`。
7. **分支用 `from`，不要把卡片手動改回去。** 失敗路徑、另一種結果是從某一步分出來的另一條路；用 `step … from <N>`，動畫標出接在哪一步，驗收腳本也會拆成獨立的場景。結果（回錯誤…）用 `expect`，造成失敗的故障用 `fault`。
8. 文件標題用說出論點的名字（「商品改了，搜尋跟著換版」），不要「XX 設計說明」。

## 內容判準

1. **以現有做法為主。** 先讀現在的程式怎麼做，再畫「要改哪裡」；不要畫一套與現況脫節的理想架構。
2. **ghost 只畫真正被考慮過、刻意不採用的路。** 它是負面決定唯一能被畫出來的地方，投報率最高，但不要拿來列一般的「沒用到」。
3. 決定表的編號（D1…、P1-1…）是跨文件的對照 key，發佈後不重排；新決定往後加。
4. 頁尾列出現況依據的檔案路徑（含 commit），讓讀者能回頭查。

## 主題與版面

1. 三種主題狀態都要正確：bare `:root` 定 light；`@media (prefers-color-scheme: dark)` 包 `:root:not([data-theme="light"])`；再一組 `:root[data-theme="dark"]`。`body` 一定要有明確背景色。
2. SVG 用 `max-width` 等於 viewBox 寬、`min-width` 約 0.8 倍，窄螢幕在自己的容器內橫向捲動，頁面本身不能橫向捲動。**一張圖寬度不超過 1000**（W7），在 1280 寬的螢幕上才不用捲動；超過就把一串連線改成上下排。
3. 字型：display 用 Noto Serif TC，內文 Noto Sans TC，資料與識別字 JetBrains Mono。
