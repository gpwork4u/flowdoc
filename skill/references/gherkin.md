# 驗收腳本：`.flow` ↔ Gherkin `.feature`

動畫頁讓人**看**每個情境的流程與各 service 此刻的狀態；同一份 `.flow` 轉成 Gherkin `.feature`，讓 cucumber 這類工具**驗證**實作真的走到那些狀態。兩者共用 parser 與 carry-over 計算，所以「畫出來的」和「驗的」不會分歧。

`.feature` 也帶著 `.flow` 的原文（`#@` 開頭的註解），兩邊是一對一的：改 `.feature` 裡的場景、步驟、表格，可以轉回 `.flow`；沒改的話轉回來和原本逐字相同。

```bash
node bin/flowdoc.js gherkin doc.flow -o doc.feature     # .flow → .feature；省略 -o 就印到 stdout
node bin/flowdoc.js flow doc.feature -o doc.flow        # .feature → .flow；列出套用了哪些修改
node bin/flowdoc.js verify doc.feature                  # 只檢查：轉得回去嗎、轉出來的 .flow 有沒有問題
```

瀏覽器 editor 的「驗收腳本」分頁也能直接改 `.feature`，按「套用到 .flow」轉回左邊（見 `docs/editor.md`）。flowdoc 只產生與讀取 `.feature` 文字，沒有任何相依套件；step definition 與 runner 放在被驗證的專案裡。

> 狀態：對應規則與互轉已實作並有測試（`test/roundtrip.test.js`）。以 E2E 驗收為主（見「用法」）；還沒有在真實專案裡實作 step definition、實際跑過。

## `.flow` → `.feature` 的對應

| `.flow` | Gherkin | 說明 |
|---|---|---|
| `title`、`lede` | `功能:` 與描述 | |
| `alias <種類> <示意 id…>` | `背景:` `假設 示意 id 對應到這次執行建立的資料：` ＋ table（示意／種類） | 每個場景開始前跑一次 |
| `part` | `場景:`，tag 是 `@part-<id>` | 標題後面括號是 actor。有 `from` 分支的段落，每條「從 init 走到葉子」的路徑各一個場景：主線一個，每個分支一個（加 `@branch`，標題接 `／<分支步驟標題>`） |
| 該段 `cards` 的起始內容（`init`） | `假設 「卡」是：` ＋ data table；沒有內容寫 `是空的` | 每張卡一行，第一行用「假設」，其餘用「而且」 |
| `store … in <元件>` | 卡片寫成 `<元件名稱> 的「卡」` | 例如 `Postgres 的「商品 → doc_id」`；inner 是 `<pod>／<inner>` |
| 路徑上各步的 `fault` | `而且 安排故障「<故障>」` | 放在「假設」的最後、第一個「當」之前：先讓故障發生，再觸發動作 |
| `step` | `當 <步驟標題>` | 點亮的元件與連線寫成下一行的註解 `# 經過：A → B（標籤）`，非同步的連線標 `［非同步］` |
| `key` 步驟 | 前一行加 `# ★ 分歧點` | Gherkin 的步驟行不能接行尾註解 |
| `from <N>` 步驟 | 前一行加 `# 分支：接第 N 步之後` | 場景裡只放路徑上的步驟；狀態從第 N 步之後接續 |
| `expect "<結果>"` | `那麼 結果應該是「<結果>」` | 放在卡片斷言前面 |
| 這一步有 set／unset／clear／note 的卡 | `那麼 「卡」應該是：` ＋ data table | **完整內容**、完全比對；不是只比對變動的那幾列。只有 note 的卡也會斷言（例如「商品不變」就斷言它仍是原來的內容） |
| `note` 的文字 | 不輸出 | 只給讀者看 |
| 這一步點亮了 `async` 連線，或卡片列在這一步的 `eventually` | `那麼 最終「卡」應該是：` | step definition 要輪詢到逾時為止 |
| 值含 `…` | 原樣保留 | 約定：示意值，step definition 只檢查「有值」 |
| 值含 `*` | 原樣保留 | 約定：萬用字元（`sku_B-*`） |
| 值裡的示意 id | 原樣保留 | step definition 換成這次執行建立的真實資料；`sku_A-r1` 這種以示意 id 開頭的值跟著換 |
| `.flow` 的每一行原文 | `#@ <原文>` 註解 | 檔頭在「功能」之前、part 在它的第一個場景之前、step 在它第一次出現的「當」之前、動畫下方的區塊在檔尾。依序接起來就是原本的 `.flow` |

`!hl`／`!gone` 是畫面上的強調，只在 `#@` 原文裡。關鍵字用 `# language: zh-TW`（`功能`、`場景`、`假設`、`當`、`那麼`、`而且`），godog、cucumber-js、behave 都支援；`#@` 是註解，runner 會忽略。

產出的樣子（`catalog-search-sync.flow` 第 1 段的第 5 步）：

```gherkin
    #@   step "記下 doc_id" key
    #@     on cat.sync->pg
    #@     desc 同步寫入：Create 回成功後，同一段程式立刻用一條條件式 UPDATE 寫回 search_doc_id、rev、digest，……
    #@     set map search_doc_id = sku_A-r1 !hl
    #@     set map search_doc_rev = 1 !hl
    #@     set map search_doc_digest = 7c1e… !hl
    # ★ 分歧點
    當 記下 doc_id
      # 經過：catalog／search_sync（改） → Postgres（同步記 doc_id）
    那麼 Postgres 的「商品 → doc_id」應該是：
      | key               | value    |
      | search_doc_id     | sku_A-r1 |
      | search_doc_rev    | 1        |
      | search_doc_digest | 7c1e…    |
```

## `.feature` → `.flow`（轉回去）

原則：**`#@` 行是 `.flow` 原文；Gherkin 看得到的內容以 Gherkin 為準。** 轉回時先用 `#@` 原文算出「原本會產生的 `.feature`」，和實際寫的比，不一樣的地方才改寫對應的 `.flow` 行，其餘逐字保留（包括註解、空行、引號與對齊）。`flow` 會列出每一處修改與它在 `.feature` 的行號。

| 在 `.feature` 改了 | `.flow` 怎麼改 |
|---|---|
| `功能:` | `title` |
| 描述 | `lede`（新增、修改、刪除） |
| 背景的表格 | 重寫 `alias`（依種類分行） |
| 一段的第一個場景名稱 `<標題>（<actor>）` | `part` 的標題與 actor |
| 一段的第一個場景的「假設」表格 | `init`：改值改那一行 `set`；加列加 `set`；刪列刪掉那一行 |
| `安排故障「…」` | 那一步的 `fault`（只能改文字；增刪故障請改 `#@ fault` 行） |
| `當 <標題>` | `step` 的標題 |
| `結果應該是「…」` | `expect`（新增、修改、刪除） |
| 「那麼」的表格 | 只處理和 `.flow` 算出來不一樣的列：這一步 `set` 過的值改那一行；帶過來的值、新的列加 `set … !hl`；刪掉的列刪掉這一步的 `set`，必要時加 `unset`；整張改成「應該是空的」加 `clear`。沒改的列照原本的變動，所以改了第 2 步的值，第 3 步以後會自然帶下去 |
| 加上或拿掉「最終」 | `eventually`（這一步點亮了 async 連線時「最終」是自動的，拿不掉，W9） |
| 多一個「當」（連同它的表格） | 新的 `step`，接在場景裡前一個「當」後面；表格變成 `set … !hl`、「結果應該是」變成 `expect`；後面的 `from <N>` 重新編號。新步驟沒有 `on`，之後在 `#@` 補上要點亮的連線 |
| 少一個「當」 | 刪掉那一步的 `.flow` 行；後面的 `from <N>` 重新編號；分支接在被刪的步驟後面的，改接它的上一步 |
| `#@` 行 | 就是 `.flow`：元件、連線、版面、`desc`、`note`、`!hl`／`!gone`、`on`、`from`、動畫下方的區塊都在這裡改 |

不能改、改了會得到 W9 的（`.flow` 照舊）：

- **推導出來的內容**：分支場景開頭照抄主線的前置步驟、分支場景的名稱、第二個以後場景的「假設」。這些在 `.flow` 裡只有一份，請改它第一次出現的地方；如果每個地方都照著改成一樣，也不會有 W9。
- **async 步驟的「最終」**、**改了卡片名稱**（`「…」` 對不到 `#@ store`）、**表格不是兩格**、**認不得的 Gherkin 行**（例如自己加的 `而且 使用者看到…`）、**斷言一張這一步沒有變動的卡**（`.flow` 沒辦法表達「不變」的斷言；需要的話在這一步加 `note`）。

會得到 E12、不輸出的：沒有 `#@` 原文（不是 flowdoc 產生的 `.feature`）、場景前面沒有 `#@ part`、步驟原文集中在段落開頭的段落（見下）增刪了場景或「當」。

**同一個值兩邊都有**：`#@ set map search_doc_rev = 1 !hl` 與表格的 `| search_doc_rev | 1 |`。以表格為準：只改 `#@` 的值、沒改表格，轉回時會被表格改回來（`flow` 的修改清單會列出來）。要改值就改表格；要改的是 `!hl`、`note`、`on` 這些表格沒有的東西，才改 `#@`。

**步驟順序和場景順序不同的段落**：一般情況下，每一步的原文放在它第一次出現的「當」前面，`.flow` 的順序就是 `.feature` 由上往下的順序。分支寫在主線中間（例如 `step "三" from 1` 寫在第 2 步與第 4 步之間）時，`.feature` 裡的順序和 `.flow` 不同，這一段每一步的原文改成集中放在段落開頭（照 `.flow` 的順序），並加一行註解說明。這種段落一樣可以改標題、表格、預期，但增刪場景或「當」要改 `#@` 行（E12）。

其他限制：

- 新增一整段或一條分支，要先在 `#@` 寫 `part`（含 `canvas`）或 `step … from <N>`，Gherkin 這邊才有地方接。
- 直接刪掉某一步的 `#@` 行（而不是刪「當」）不會重新編號 `from <N>`；要刪步驟請刪「當」，或刪完自己檢查 `from`。
- `#@` 以外的 `#` 註解（`# 經過：…`、`# ★ 分歧點`）是推導出來的，轉回時不看，下次產生會重寫。

## 用法：以 E2E 驗收為主

`.feature` 對著部署好的環境（例如 staging）跑，不為了測試改 service 的程式：

- 每個場景**只有第一個「當」從外部觸發**（actor 的動作：上架、賣家刪除、跑 CLI）。
- 之後的「當」是內部步驟（組文件、上傳、Create…），step definition 實作成「**等到這件事發生**」（查 log、查狀態，或直接 no-op），「那麼」當檢查點。
- 「最終…應該是」輪詢到逾時為止；其他「那麼」查一次。

同一份 `.feature` 也能拿來做整合測試（用 test hook 逐步驅動），差別只在 step definition。

## step definition 要做什麼

固定的幾條，加上每個動作、每種故障各一條：

| step | 做什麼 |
|---|---|
| `示意 id 對應到這次執行建立的資料：` ＋ table | 每一列依種類建一筆真實資料（商品、使用者…），記下「示意 id → 真實 id」；之後所有表格的值、`結果應該是` 的文字都先做替換 |
| `(?:(.+) 的)?「(.+)」是：` ＋ table／`…是空的` | 把那張卡準備成這個狀態（seed DB、建文件…）；第一個 group 是 service，沒有就靠卡片名稱判斷 |
| `安排故障「(.+)」` | 每種故障一條：讓那個故障在接下來的動作裡發生（mock、fault injection、關掉下游…） |
| `(最終 ?)?(?:(.+) 的)?「(.+)」應該是：` ＋ table／`…應該是空的` | 去 service 查那張卡，和 table 完全比對；有「最終」就輪詢到逾時為止 |
| `結果應該是「(.+)」` | 比對觸發動作的回應（錯誤碼、回傳內容） |
| `當 <步驟標題>` | 每個標題一條：場景的第一個「當」觸發動作，其餘等到這件事發生 |

`.feature` 不綁 runner：Go 用 godog、JavaScript 用 cucumber-js、Python 用 behave。

## 已決定

- **分支用 `step … from <N>`。** 原本用 `clear` 再 `set` 把卡片改回去，`.feature` 會把分支接在主線最後一步後面，語意錯誤。現在分支自成一個場景，狀態從第 N 步之後接續。
- **只給讀者看的說明用 `note`，結果用 `expect`。** `set map — = 不變`、`set doc Delete = 回錯誤` 會變成沒有意義的斷言。範例裡的 digest 比較、purge、「待補／跳過」、查詢條件都用 note。
- **以 E2E 驗收為主**（見「用法」）。
- **示意 id 在 `.flow` 裡用 `alias` 宣告**，不只是 step definition 的約定：宣告了 verify 才能檢查重複，`.feature` 的「背景」也才列得出要建哪些資料。替換規則（字串前綴、`…`、`*`）由 step definition 實作。
- **失敗分支的故障用 `fault`**，轉成場景開頭的「安排故障」。E2E 裡故障一定要在觸發之前就位，不能等到那個「當」才佈置。
- **卡片用 `store … in <元件 id>` 標出它在哪裡。** store 是全頁共用，元件 id 是每段各自的；用 id（不是自由文字）才檢查得到「卡片在這段的圖上找不到它的 service」（W8），名稱則從那一段的元件取。
- **「最終」用 `eventually <卡>` 明確標出**，不自動推導。「前面有非同步、後面全部輪詢」會連同步該立刻成立的斷言（例如商品列已刪）一起放寬，把真正的 bug 藏起來；所以只自動處理「這一步自己點亮了 async 連線」，其餘由撰寫者標。範例第 3 段「再刪商品資料」標了 `eventually doc`，商品那張卡仍是立即斷言。
- **一對一靠 `#@` 原文，不另創一套語法。** `.feature` 只多了註解，runner 不受影響；`.flow` 的每一行都在，所以沒改時轉回來逐字相同，元件、連線、版面這些 Gherkin 表達不了的東西也不會掉。
- **Gherkin 看得到的以 Gherkin 為準，表格只改「不一樣的列」。** 改 `.feature` 的人通常改的是場景與表格；只改不一樣的列，前面步驟的修改才會自然帶到後面，不會在每一步都多出一行 `set`。
